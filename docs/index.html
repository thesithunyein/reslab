The problem

P-hacking is the reproducibility crisis.

Under pressure, researchers try a different test, peek at the data, or drop an outlier — until something becomes significant. That is p-hacking, and it quietly corrupts a large share of published findings. Generic AI data tools make it worse: they answer confidently, never check whether an analysis was appropriate, and give users no guardrail between exploration and claim-making.

ResLab is built the other way. Every statistic is computed, not generated. Every result passes code-level verification before it can enter the record. Every action lands in a hash-chained audit log where silent edits are impossible. And a deterministic detector suite flags the classic p-hacking patterns — for review, with the human always deciding.

How it works

The honest research flow, enforced by design.

01 · DESIGN

Before any data

Hypothesis, outcome, planned test, alpha, sample size — plus power analysis that tells you what effect you can actually detect with the sample you can afford.

02 · PRE-REGISTER

Locked, tamper-evident

The plan is sealed with a SHA-256 checksum and recorded in a hash-chained audit log. Revisions create new versions — the original is never mutated.

03 · ANALYZE

Real numbers only

t, Welch, paired t, ANOVA, Pearson, Mann-Whitney, Levene, Jarque-Bera — a real statistics engine computes every value. No LLM generates a number.

04 · TWO LANES

Confirmatory vs exploratory

Claims come only from the pre-registered lane. Post-hoc exploration is allowed — but labeled and walled off. Hypotheses, never conclusions.

05 · DETECT

The guardian

Test switching, tail switching, outcome switching, optional stopping, subgroup slicing, undeclared outlier removal, multiple comparisons — each flagged with its bias explained.

06 · PROVE

Reproducible forever

The audit chain verifies nothing was changed, and a reproducibility recipe lets anyone replay the exact analysis — same data, same tests, same numbers.
